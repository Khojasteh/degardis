# Instructions for AI agents

Use this file when changing this repository. Authoring rules belong in the manual topics, other product behavior in `docs/`, and implementation in code.

Do not edit this file without explicit owner permission. Do not bump the package version or `CURRENT_FORMAT_VERSION` without explicit owner permission.

## Repository

Degardis is a Python CLI compiler from authored skill sources to installable agent bundles.

- `degardis/` — product code and packaged manual/check explanations.
- `docs/` — human documentation.
- `tools/` — repository-only utilities.
- `examples/structured-summary/` — the only public example; it must validate and exercise every format construct.
- `tests/fixtures/skills/demo/` — synthetic test sources; malformed cases are intentional. `alpha` covers every construct/placement and `beta` supports multi-skill discovery/build tests.
- `.artifacts/` — untracked build scratch space.

## Verify changes

Python 3.10+ is supported; CI runs 3.10 and 3.14. Install with:

```console
python -m pip install -e ".[lint]"
```

Run the checks relevant to the change:

```console
python -m ruff check .
python -m unittest discover -s tests -v
python -m tools.generate_manual --check
python -m degardis validate examples/structured-summary
```

Build only into scratch output such as `.artifacts`; rebuilds replace an existing artifact with the same skill name. Before changing bundle behavior, read `tests/test_conformance.py`: its cases define the format guarantees.

## Contracts to preserve

- **Read path:** `SKILL.md` routes each outcome a request asks for directly to one task page; that page contains the task's complete knowledge closure. Do not add an intermediate page. A task page links another task page only through a declared hand-off. The facet index is the only runtime lookup; tasks never select facets, and removing generated facets must not change `SKILL.md` or task pages.
- **Source identity:** type comes from its namespace, id from the file stem, metadata from frontmatter, and content from the Markdown body. Source files do not declare ids; renaming the file renames the construct.
- **Authored text stays authored:** only `wording.py` owns compiler prose. Construct bodies come from the skill being compiled, and principle references resolve only within that skill. Compilation may re-level headings, render inline references, and fold hard-wrapped prose; it must not paraphrase, merge, summarize, invent, reorder, or silently drop authored material.
- **Selection is authored; placement is compiled:** owners, dependencies, and hand-offs are explicit declarations; the compiler places from them and never infers or auto-promotes. Inline references that make an owner are declarations too: `[[guide:ID]]` in a task, a knowledge unit, a facet, or a guide; the `markdown` manual topic defines what each one owns. Only `skill.yaml` owns principles; a guide owns the guides its `requires` names, and ownership is not transitive. Every declared relationship must affect generated output.
- **Dependencies and hand-offs are explicit:** prose never creates either. Placement changes only through declarations, inline ones included.
- **Budgets model one read:** the root is startup cost; a task page is one task load; separately linked pages are additional loads. Change a budget only to reflect reader cost, not a round-number preference.
- **References:** a field that fixes the namespace takes bare ids; only a field that accepts more than one kind takes qualified references.
- **Diagnostics are a closed contract:** every check code is a literal, has an explanation file, and is exercised by a case that reports it. Explanations live in `degardis/explain_codes/<code>.yaml`; shared wording lives in `degardis/explain_codes/wording/`. Do not write explanation prose in Python.
- **Code spelling:** `namespace.hyphenated-name`, except source-key names keep the key spelling (for example `interface.short_description-length`). Required, unknown, and invalid fields use `<ns>.missing-<key>`, `<ns>.unknown-field`, and `<ns>.invalid-<key>`. Nested list-item failures keep the enclosing item's code.
- **Checks collect:** report all findings, and all unknown `explain` codes at once. Deduplication must not collapse distinct findings; messages must identify what was refused, not only its file.
- **One manual source:** `degardis/manual_topics/` contains every printable topic and `topics.yaml` its catalog/order. `docs/manual.md` is generated from those topics plus `tools/manual_template.md`; never edit it directly. Every manual rule must be reachable through `degardis manual TOPIC`.
- **One validation result:** `validate`, `inspect`, and `build` run the same checks over the same compilation and use the same exit status. `--only`/`--all` change reporting only. Validation belongs in `validate.py`; inspection shapes results but does not decide validity.
- **Machine interface:** the inspect report is the only machine-readable build view. Do not emit plans, closures, source maps, coverage files, or similar side reports.
- **Build integrity:** writes are atomic per skill. A failed skill leaves its old artifact unchanged; completed siblings remain; warning promotion stops that skill before writing. Rebuilding the same source with the same compiler is byte-identical across hosts.
- **CLI help:** `degardis -h COMMAND` and `degardis COMMAND -h` are equivalent.
- **Version source:** `degardis/__init__.py:__version__` is authoritative; release tags are `v<version>`.
- **Report shape is API:** row columns/order and summary lines are tested literally. Help wording is not a compatibility surface.
- **Root stays minimal:** its section order is fixed, empty sections disappear, and anything it can point to stays off the root. No knowledge, facet catalog, resource index, or hand-off belongs there.
- **Scope:** Degardis establishes artifact integrity, not whether a skill is useful. Do not add commands, metrics, or documentation that imply behavioral grading.

## Audience boundaries

- `README.md` and `docs/`: humans choosing, authoring, or operating Degardis. Describe public inputs, outputs, guarantees, and observable runtime behavior; do not document the generated control mechanism used to achieve that behavior. An implementation-only change must not require a public-documentation change.
- `degardis manual`: primarily authoring agents, also humans. State source rules and observable artifact behavior tersely; do not expose internal algorithms, modules, processing structures, generated bookkeeping, or control-protocol vocabulary. Artifact-layout topics may name paths a reader must use. State validation rules and repairs without check codes; check-code detail belongs to `explain_codes/`.
- Installed packages ship no `docs/`; CLI help must be self-contained. Keep help brief; long help means a manual topic is incomplete.
- `inspect` output/help: AI agents; compact and line-oriented.
- `validate`, `list`, `build`: humans at a terminal. Agents needing structured facts use `inspect`.
- `explain`: whoever repairs a source; state trigger, impact, and repair. The repair is the impact's last sentence, or a `resolution` when it is not.
- Generated `SKILL.md` and task pages: the agent executing the authored skill.
- Diagnostics: name the problem, location, and check code.

## Documentation ownership

State each concept once, in its owner. Elsewhere, link to it from `README.md` and `docs/`, or name the topic in `topics.yaml` `related` for the manual; topic prose carries no cross-references. CLI help and each `explain` entry must stand alone, so they may restate briefly what they need.

- `README.md`: landing page; summarizes and links, owns no rule.
- `docs/getting-started.md`: the shortest authoring loop; links to the manual for constructs and rules.
- `docs/cli.md`: commands, options, source paths, output encoding, and exit status.
- `docs/artifact-format.md`: bundle contents, host metadata, runtime behavior, and folder/ZIP details.
- Manual topics: source rules, observable artifact behavior, and how validation, inspection, and build behave. `overview` owns the read path; `markdown` owns source identity, body handling, and inline references, including which bodies may use them and what they own; `relationships` owns knowledge closures, guide lists, and conditions; each construct topic owns its fields and construct-specific rules; `validation` owns what a pass means; `build` owns replacement, atomicity, and reproducibility.

None of these teaches how to author a good skill or how the compiler works internally.

## Code conventions

- Start modules with `from __future__ import annotations`; annotate public signatures and keep Python 3.10 compatibility.
- Use docstrings for rationale/invariants, not restating names. `analysis.py` and `markdown.py` are the style reference.
- Match surrounding formatting; no formatter is authoritative.
- Generated prose in `wording.py` is not a compatibility surface. Do not pin its literal phrasing in tests; test observable behavior or structure instead, unless the text itself is an explicit public contract.
- Ask before adding any dependency, including test-only dependencies.
- Any failure covered by a check carries its code through every path; one-off failures with no check carry none.
- Use American spelling.

## Change map

| Change | Also update |
| --- | --- |
| Check | Literal code, `explain_codes/<code>.yaml`, a firing test, and any affected manual rule |
| Construct schema/kind | `sources.py`, placement in `analysis.py`, rendering in `render.py`, and its manual topic |
| Required field | Call-site `missing` code, explanation file, and required-field manual row |
| `content` key | `content.py`, `sources.py` dispatch, invalid check, manifest topic, example, fixtures |
| Manifest/interface key | `registry.py`, `content.py`, `package.py`, and `manifest` or `interface` topic |
| Page composition/placement | `analysis.py`, reference checks in `validate.py`, `render.py`, and conformance tests; update the `relationships` or construct topic only if authored semantics or observable loading behavior changes |
| Routing rule or hand-off semantics | `wording.py`, conformance tests, `tasks` manual topic (`relationships` for conditions), and `docs/artifact-format.md` runtime behavior |
| CLI command/option | `cli.py` help/examples, `docs/cli.md`, README command list |
| Inspect dimension/row | `output.py`, `inspection.py`, `inspection` topic, `docs/cli.md` |
| Generated section wording | `wording.py` only |
| Generated runtime control mechanism | implementation and conformance tests only; update public docs only if observable behavior changes |
| Generated page path | `bundlepaths.py` only |
| Manual topic | Topic file, `topics.yaml` if metadata/order changes, CLI help references, regenerate `docs/manual.md` |
| Bundle layout | `package.py`, `bundlepaths.py`, and conformance cases; update `docs/artifact-format.md` only when the public bundle contract changes |
| Source format | `CURRENT_FORMAT_VERSION` and every affected manual topic |
| Package version | `degardis/__init__.py` only; release tag `v<version>` |
